1.4 Git в EDT: репозиторий, коммиты, ветки

Глава 1 · Задача 4. Git в EDT

Цель: научиться вести историю изменений конфигурации: коммитить, создавать ветки, переключаться между ними и сливать их. Где работаем: проект Uchebnaya в рабочей области ~/1C/workspaces/edu. Git локальный: работает на твоём Маке, без интернета и без аккаунтов. GitHub — отдельный шаг в конце.

💡 Названия пунктов меню в русской EDT иногда отличаются от моих. Поэтому в скобках даю английские — по ним проще искать.

0. Понятия за минуту

Понятие Что это Аналогия
Репозиторий Скрытая папка .git внутри проекта. В ней хранится вся история Альбом со всеми фото проекта
Коммит Снимок всех файлов проекта в момент времени с подписью «кто, когда, что сделал» Одно фото в альбоме
Индекс(staging) Список изменений, которые попадут в следующий коммит Стопка фото, отобранных для вклейки
Ветка Отдельная линия истории Черновик, который не портит чистовик
master / main Основная ветка, создаётся вместе с репозиторием Чистовик
Слияние(merge) Перенос изменений из одной ветки в другую Переписать удачный черновик в чистовик
HEAD Указатель «где я сейчас»: текущая ветка и последний коммит Закладка в альбоме

Что попадёт в репозиторий

Uchebnaya/
├── .git/            ← история (создаст Git, папка скрытая)
├── .project         ← служебный файл проекта
├── .settings/       ← настройки проекта
├── DT-INF/          ← настройки проекта EDT
└── src/             ← вся конфигурация: объекты (.mdo), модули (.bsl), формы

Не попадёт (лежит вне папки проекта, и это правильно):

  • ~/1C/bases/ — базы. Это данные, а не код; новая база собирается из проекта по ▶.
  • ~/1C/workspaces/edu/.metadata — настройки EDT.
  • ~/1C/backups/ — бэкапы.

💡 Почему EDT дружит с Git, а конфигуратор нет: в EDT конфигурация хранится как текстовые файлы, и Git видит каждую изменённую строку. В конфигураторе конфигурация — один двоичный файл, и Git видит только «файл изменился».

Шаг 1. Имя и почта для коммитов

Это подпись под каждым коммитом. Она никуда не отправляется.

  1. Открой настройки: Cmd + ,
  2. Групповая разработка (Team) → Git → Конфигурация (Configuration).
  3. Вкладка Настройки пользователя (User Settings) → Добавить запись (Add Entry):
  4. ключ user.name, значение — твоё имя, например Ivan Petrov;
  5. ключ user.email, значение — почта.
  6. Применить и закрыть (Apply and Close).

💡 Если есть аккаунт на GitHub, укажи ту же почту, что там: при выгрузке коммиты сами привяжутся к профилю.

⚠️ Пропустишь этот шаг — EDT спросит имя при первом коммите. Ничего страшного, но лучше сразу.

Шаг 2. Создать репозиторий

  1. В навигаторе — правой кнопкой по проекту Uchebnaya.
  2. Команда (Team) → Общий доступ к проекту (Share Project).
  3. Выбери Git → Далее.
  4. Создай новый репозиторий: кнопка Создать (Create).
  5. Проверь путь — это главное. Репозиторий должен оказаться в папке проекта: 
    /Users/<ты>/1C/workspaces/edu/Uchebnaya/.git      ✅
/Users/<ты>/1C/workspaces/edu/.git                ❌ (вся рабочая область)
  6. Готово (Finish).

Как проверить, что получилось

  • В навигаторе рядом с проектом появится имя ветки: Uchebnaya [Uchebnaya master] или похожее.
  • У файлов появятся значки Git: «?» или «+» — значит, новые и ещё не закоммиченные.
  • В Finder в папке Uchebnaya появилась скрытая .git (показать скрытые: Cmd + Shift + .).

💡 Основная ветка может называться master или main — зависит от версии Git. Разницы нет.

Шаг 3. Открыть нужные панели

Все три открываются через Окно → Показать панель → Другие… → Git:

Панель Зачем
Индексирование Git (Git Staging) Собирать коммиты: что изменилось, что войдёт, сообщение
История (History) Смотреть список коммитов
Репозитории Git (Git Repositories) Ветки, удаление веток, общая картина

💡 Перетащи их в нижнюю часть окна, рядом с «Ошибками конфигурации», — так они всегда под рукой.

Шаг 4. Первый коммит

  1. Открой панель Индексирование Git.
  2. Слева вверху — Неиндексированные изменения (Unstaged Changes): там все файлы проекта.
  3. Нажми ++ («Добавить всё в индекс», Add all). Файлы переедут в Индексированные изменения (Staged Changes).
  4. В поле Сообщение фиксации (Commit Message) напиши: Начальная конфигурация: справочник Товары, подсистема.
  5. Нажми Фиксировать (Commit).

⚠️ Кнопку Фиксировать и отправить (Commit and Push) не нажимай: удалённого репозитория пока нет, будет ошибка.

Проверь

Правой кнопкой по проекту → Команда → Показать в истории (Show in History). В панели «История» должен появиться один коммит с твоим именем и сообщением.

Как писать сообщения коммитов

  • Коротко и по сути: что сделано, а не «изменения» или «правки».
  • ✅ Добавлен документ ПриходТовара · Исправлен расчёт суммы в форме
  • ❌ fix · 123 · доработки
  • 💡 Правило: один коммит — одна законченная мысль. Добавил документ и проверил — коммит.

Шаг 5. Создать ветку

  1. Правой кнопкой по проекту → Команда → Переключить на (Switch To) → Новая ветка (New Branch).
  2. Имя ветки: feature/prihod.
  3. Галочка Выгрузить новую ветку (Check out new branch) должна стоять — тогда ты сразу перейдёшь в неё.
  4. Готово.

Проверь

В навигаторе рядом с проектом теперь [... feature/prihod].

💡 Принятые префиксы имён веток: feature/ — новая функциональность, fix/ — исправление ошибки. Латиница, без пробелов.

Шаг 6. Сделать доработку в ветке

Создай документ ПриходТовара:

  1. Правой кнопкой по «Документы» → Создать. Имя: ПриходТовара.
  2. Табличная часть Товары с реквизитами:
  3. Товар — тип СправочникСсылка.Товары;
  4. Количество — Число (10, 3);
  5. Цена — Число (15, 2).
  6. Добавь документ в подсистему «Товары»: вкладка Подсистемы внизу редактора.
  7. Сохрани: Cmd + Shift + S.
  8. Запусти ▶ и проверь, что документ создаётся и записывается.

Теперь закоммить:

  1. Панель Индексирование Git → ++.
  2. Сообщение: Добавлен документ ПриходТовара.
  3. Фиксировать.

💡 Посмотри на список изменённых файлов перед коммитом: появилась папка src/Documents/ПриходТовара/ и изменились файлы подсистемы и конфигурации. Так выглядит любая доработка «изнутри».

Шаг 7. Вернуться в основную ветку

  1. Правой кнопкой по проекту → Команда → Переключить на → master (или main).
  2. Посмотри в навигатор: документа ПриходТовара нет. Он существует только в ветке feature/prihod.

⚠️ Перед переключением веток всё должно быть закоммичено. Иначе Git либо откажется переключаться, либо перенесёт несохранённые изменения в другую ветку, и получится путаница.

⚠️ Про базу. Если сейчас нажать ▶, EDT загрузит в базу конфигурацию без документа и удалит его таблицу вместе с введёнными документами. В учебной базе это не страшно, но запомни: ветки меняют проект, а база просто подстраивается под проект при запуске.

Шаг 8. Слить ветку в основную

  1. Убедись, что ты в master (смотри имя ветки в навигаторе).
  2. Правой кнопкой по проекту → Команда → Слить (Merge).
  3. В списке Локальные ветки (Local) выбери feature/prihod.
  4. Слить (Merge).

Результат будет Fast-forward: Git просто передвинул master вперёд до последнего коммита ветки, потому что в master за это время ничего не менялось.

Проверь

  • Документ ПриходТовара снова в навигаторе.
  • В «Истории» видны оба коммита.
  • ▶ — документ работает.

Шаг 9. Удалить отработанную ветку (по желанию)

Ветка слита, она больше не нужна.

  1. Панель Репозитории Git → твой репозиторий → Ветви (Branches) → Локальные (Local).
  2. Правой кнопкой по feature/prihod → Удалить ветвь (Delete Branch).

💡 Удалять можно только ветку, в которой ты сейчас не находишься.

Бонус 1. Отменить несохранённые изменения

Наделал лишнего и хочешь вернуться к последнему коммиту:

  • Один объект: правой кнопкой по нему → Заменить на (Replace With) → Последняя фиксация HEAD(HEAD Revision).
  • Весь проект: правой кнопкой по проекту → Команда → Сбросить (Reset) → режим Полный (Hard).

⚠️ Полный сброс удаляет все незакоммиченные изменения без возможности вернуть. Перед ним подумай дважды.

Бонус 2. Конфликт слияния (потренироваться заранее)

Конфликт — это когда в двух ветках изменили одно и то же место по-разному, и Git не знает, какой вариант правильный.

  1. Создай ветку test/conflict-a. В ней поменяй синоним справочника «Товары» на Товары А → коммит.
  2. Вернись в master, создай ветку test/conflict-b. Поменяй синоним на Товары Б → коммит.
  3. Вернись в master, слей test/conflict-a — пройдёт без проблем.
  4. Слей test/conflict-b — конфликт.
  5. Правой кнопкой по проекту → Команда → Средство слияния (Merge Tool). Выбери, какой вариант оставить.
  6. Добавь результат в индекс (++) → Фиксировать.

💡 Конфликты — нормальная часть работы. Пугаться не надо, разбираться — да.

Что дальше: GitHub

Когда задача выполнена, можно выгрузить репозиторий на GitHub — это и резервная копия вне Мака, и будущее портфолио:

  1. Создай на GitHub приватный пустой репозиторий (без README).
  2. Создай токен: Settings → Developer settings → Personal access tokens. Он вводится вместо пароля.
  3. В EDT: ПКМ по проекту → Команда → Отправить (Push) → адрес репозитория, логин, токен.
  4. Дальше после каждого коммита — Push.

Подробно — курс, модуль 4, уроки 07–10.

⚠️ На личный GitHub — только учебные проекты. Код компании и клиентов туда не выкладывают никогда.
